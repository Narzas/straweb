식당에서 밥을 먹고 받은 영수증을 폰으로 찰칵 찍으면, 잠시 후 "토큰 N개 적립 완료" 푸시가 오는 서비스. 말로는 한 줄이지만, 이걸 진짜로 만들어보면 **사용자한테는 안 보이는 자잘한 결정들이 잔뜩** 튀어나온다.

- 영수증을 어떻게 "이거 진짜다" 확인할까?
- 사용자가 같은 영수증을 두 번 올리면 어떻게 막을까?
- 블록체인 트랜잭션이 1초 걸리는데, 그 동안 사용자를 기다리게 할까?
- 사진을 좀 자르고 밝기를 바꿔 다시 올리면?
- 가짜 승인번호를 만들어 합성 영수증을 올리면?

이 글은 **외식 토큰 적립 서비스를 Kaia 체인 위에서 설계할 때** 마주친 그런 결정들을 시퀀스 다이어그램으로 정리한 기록이다. 코드는 없다. 흐름과 이유만 있다.

## 1. 왜 5개로 쪼갰나

처음엔 "그냥 백엔드 하나로 다 처리하면 안 되나?" 싶었다. 근데 막상 뜯어보면 **하는 일의 성격이 너무 다르다.**

| 컴포넌트 | 역할 | 왜 분리했나 |
|---|---|---|
| **User App** | 사진 찍기, 결과 보기 | 사용자 단말 |
| **API Server** | 비즈니스 규칙 검증, DB 쓰기, 블록체인 호출 | 핵심 두뇌 |
| **분석 서버 (Analyzer)** | QR 검증 + OCR 텍스트 추출 | CPU/GPU 무거움. 따로 빼야 API가 안 죽음 |
| **DB** | 영수증·적립 내역 영구 보관 | 사실의 원천 |
| **Kaia 블록체인** | 토큰 발행 (mint) | 위변조 불가능한 발행 장부 |

특히 **분석 서버를 따로 두는 게 중요하다.** OCR은 한 번 돌리면 1~3초씩 걸리는 무거운 작업이다. API 서버에 같이 두면 OCR 도는 동안 다른 사용자 요청이 다 밀린다. 분석 서버는 따로 띄워두고 큐로 호출한다.

---

## 2. 시작은 사용자 앱에서

사용자가 영수증을 찍어 [적립하기]를 누르면 **API 서버로 사진이 올라간다 (단계 1).**

이때 같이 보내는 게 **액세스 토큰** — 로그인할 때 발급받은 신분증이다. 서버는 이 토큰을 보고 "아, 누가 이걸 보냈는지" 안다.

> ### JWT? 액세스 토큰? 헷갈리면 그냥
>
> "로그인 후 받는 종이 신분증" 이라고 생각하면 된다. 매번 ID/비번을 다시 보내지 않고, 처음 로그인 때 받은 토큰을 같이 보내서 "나야"를 증명한다.
>
> 이 프로젝트에서는 **액세스 토큰(1시간) + 리프레시 토큰(30일)** 조합을 쓴다. 액세스가 만료되면 앱이 리프레시로 알아서 새로 받아오니, 사용자는 한 달에 한 번만 재로그인하면 된다.

---

## 3. 분석 서버로 간 사진은 어떻게 처리되나

API 서버는 받은 사진을 분석 서버로 던진다 (단계 2). 분석 서버 안에서 두 갈래로 갈린다 (단계 3).

### QR이 있으면 — 위조 불가능

요즘 외식 매장 영수증에는 **QR 코드를 인쇄해 넣을 수 있다.** 우리 시스템은 제휴 매장에 가게별 시크릿 키를 발급한다. 가맹점 POS는 영수증을 출력할 때 **이 시크릿으로 (사업자번호 + 승인번호 + 금액 + 일시)에 서명한 QR**을 같이 찍는다.

분석 서버가 QR을 발견하면:

1. QR 안의 페이로드와 서명을 분리
2. 가맹점 시크릿(서버에 저장)으로 서명 검증
3. 서명이 맞으면 **이건 진짜 그 매장에서 발급된 영수증** (위조 0%)

### QR이 없으면 — OCR fallback

QR이 없거나 인식 실패한 경우, **OCR로 텍스트를 추출한다.** 영수증 사진에서 가게명, 사업자번호, 결제일시, 금액, 승인번호 같은 필드를 글자로 읽어낸다.

OCR은 완벽하지 않다. 신뢰도(confidence) 점수가 같이 나오는데, 0.85 미만이면 "이거 잘 안 읽혀" 신호다. 이런 건 사람 검토 큐로 넘긴다.

분석 결과는 이런 모양으로 API 서버에 돌아온다 (단계 4):

```json
{
  "source": "QR",                       // 또는 "OCR"
  "merchant_brn": "123-45-67890",
  "payment_dt":   "2026-05-01 18:23",
  "amount":       25000,
  "serial":       "00012345678",
  "confidence":   1.0                    // QR이면 1.0, OCR이면 0.85+
}
```

핵심은 **`source` 필드**다. 이걸 보고 다음 단계의 검증 강도를 조정한다.

## 4. 적립 자격 검증 — QR이냐 OCR이냐에 따라 다르다

API 서버가 결과를 받으면 "이거 적립할 자격이 되는가" 검증한다 (단계 5).

### 공통 검증 (QR / OCR 무관)

- 가게가 **우리 제휴 매장 테이블**에 있는가?
- **같은 영수증으로 이미 적립한 적 없는가?** (가장 중요 — 아래에서 자세히)
- 결제일이 **최근 7일 이내**인가? (오래된 영수증 재활용 차단)
- 사용자 **일일 적립 한도** 안 넘었나?

### OCR 경로만 추가 검증

- 신뢰도 0.85 이상
- 모든 필수 필드 (사업자번호 / 승인번호 / 금액 / 일시) 파싱 성공

QR 경로는 시크릿 서명이 이미 통과됐기 때문에 신뢰도 검증이 필요 없다. OCR 경로는 텍스트 자체에 오인식 가능성이 있으니 한 겹 더 본다.

---

## 4-1. 검증 단계 자세히 들여다보기

"검증한다"는 말 뒤에는 실제로 **3개의 층**이 차례로 쌓여 있다.

### 1층 — Analyzer: 영수증 내용 읽기

**QR 경로**

| 단계 | 하는 일 |
|---|---|
| ① 페이로드 분리 | QR 데이터에서 본문(사업자번호·승인번호·금액·결제일시)과 서명을 분리 |
| ② 서명 검증 | 가맹점 시크릿 키로 HMAC-SHA256 재계산 → QR 안의 서명과 일치 여부 비교 |
| ③ 필드 추출 | 일치 시 4개 필드를 구조체로 변환, confidence=1.0 |

단계 ②에서 서명이 단 한 글자라도 다르면 즉시 탈락. 시크릿 키 없이는 올바른 서명을 만들 수 없으니, 아무리 정교하게 영수증을 합성해도 이 검증은 통과할 수 없다.

**OCR 경로**

| 단계 | 하는 일 |
|---|---|
| ① 이미지 전처리 | 기울기 보정, 노이즈 제거, 대비 강화 |
| ② 텍스트 영역 감지 | 영수증 내 텍스트 블록 좌표(bbox) 추출 |
| ③ 문자 인식 | 각 블록을 문자열로 변환, 단어마다 신뢰도(0~1) 부여 |
| ④ 필드 파싱 | 정규식으로 가게명·사업자번호·승인번호·금액·결제일시 추출 |
| ⑤ 신뢰도 집계 | 핵심 필드(사업자번호·승인번호) 신뢰도 평균 → **0.85 미만이면 검토 큐로 이관** |

### 2층 — Server: 비즈니스 자격 검사

Analyzer 결과를 받은 API 서버가 이번엔 **"이 사람이 지금 적립할 자격이 있나"** 를 따진다.

| 검사 항목 | 통과 조건 | 실패 시 |
|---|---|---|
| 제휴 가맹점 | DB 가맹점 테이블에 해당 사업자번호 존재 | 거절 (미제휴 매장) |
| 결제일 유효 | 오늘 기준 **7일 이내** | 거절 (기간 만료) |
| 중복 적립 | `merchant_brn + serial + payment_dt` 조합이 DB에 없음 | 거절 (이미 적립된 영수증) |
| 일일 한도 | 사용자 당일 적립 횟수 < 설정값 (예: 3건) | 거절 (한도 초과) |
| OCR 신뢰도 | (OCR 경로만) 평균 confidence ≥ 0.85 | 검토 큐로 이관 |

### 3층 — Kaia 컨트랙트: 발행 권한 최종 확인

서버가 `mint()`를 호출하면 스마트 컨트랙트가 마지막으로 확인한다.

```
onlyRole(MINTER_ROLE)
```

서버 지갑(KMS에 보관)만 이 역할을 갖는다. 사용자가 자기 지갑으로 직접 컨트랙트를 호출해도 **컨트랙트 수준에서 reject** — 블록체인 단에서 이중 잠금이 걸려 있어, 서버를 우회한 발행 자체가 불가능하다.

> **검증 3층 요약**
>
> | 층 | 담당 | 핵심 질문 |
> |---|---|---|
> | 1층 | Analyzer | 이 영수증 내용이 진짜인가? |
> | 2층 | Server | 이 사람이 지금 적립할 자격이 있나? |
> | 3층 | Kaia 컨트랙트 | 호출자가 발행 권한을 갖고 있나? |
>
> 셋 중 하나라도 NO 면 적립은 일어나지 않는다.

### OCR 경로의 구조적 약점 — 승인번호 위조

검증 3층을 모두 통과해도 **OCR 경로에는 막을 수 없는 공격이 하나 있다.**

제휴 가맹점 사업자번호는 공개 정보다 (영수증 한 장만 받으면 된다). 거기에 아무 숫자로 만든 가짜 승인번호를 인쇄해서 제출하면:

| 검사 | 결과 | 이유 |
|---|---|---|
| 제휴 가맹점 확인 | ✅ 통과 | 실제 가맹점 번호 사용 |
| 결제일 7일 이내 | ✅ 통과 | 날짜 직접 기입 |
| 중복 적립 확인 | ✅ 통과 | 처음 쓰는 번호 조합 |
| OCR 신뢰도 | ✅ 통과 | 선명하게 인쇄하면 0.9 이상 |
| **승인번호 진위** | ❌ 미확인 | **이 번호가 실제 발급됐는지 확인 수단 없음** |

결국 **적립이 성공한다.** 국세청 현금영수증 진위확인 API가 존재하지만 일반 기업은 사용할 수 없어 (본인 영수증 본인 조회 전용), 서버 단에서 직접 검증하는 방법이 없다.

**그래서 "완벽한 차단" 대신 "위조해도 이득이 작고, 대규모 시도는 눈에 띈다" 구조를 만드는 게 현실적 목표다.**

| 완화책 | 효과 | 한계 |
|---|---|---|
| OCR 적립량을 QR보다 낮게 설정 | 위조해도 이득이 줄어든다 (QR 대비 50~70%) | 소량 위조는 여전히 가능 |
| 1인당 월 적립 한도 | 연속 위조로 대량 이득 취하는 시나리오 차단 | 여러 계정으로 분산 시 우회 |
| 가맹점별 일일 제출 건수 캡 | 특정 가맹점 집중 공격 시 플래그 | 임계값 초과 건은 수동 검토 큐 |
| 기기 fingerprint 추적 | 동일 기기에서 다수 제출 시 감지 | 기기 변경 시 우회 가능 |
| 도입 초기 샘플 수동 검수 | 이상 패턴 조기 발견 | OCR 제출의 일정 % 랜덤 검토 |
| VAN사/카드사 연동 | 승인번호 실존 여부 직접 확인 — 가장 확실 | B2B 계약 필요, 소규모 서비스엔 허들 높음 |

> **결론:** OCR 경로는 보조 수단으로만 운영하고, 가능하면 QR 경로로 유도하는 게 맞다. 승인번호 위조를 원천 봉쇄하려면 VAN사 연동이 필요하고, 그게 어려운 초기엔 적립 한도 + 사후 감사 조합으로 피해 상한선을 낮춘다.

## 5. 같은 영수증 두 번 차단은 어떻게?

가장 자주 시도되는 부정 사용 시나리오. **DB에 복합 UNIQUE 제약**으로 막는다.

```sql
UNIQUE (merchant_brn, serial, payment_dt::date)
```

= **사업자번호 + 승인번호 + 결제일** 조합이 단 하나만 들어갈 수 있다.

### 사용자가 시도할 만한 변형들

| 시나리오 | 차단 방법 |
|---|---|
| 같은 영수증을 그대로 재업로드 | UNIQUE 제약 위반 → 거절 |
| 사진을 자르고 밝기 바꿔 재업로드 | **이미지가 달라도** 분석 결과 (사업자번호+승인번호)가 같음 → 거절 |
| 다른 계정 만들어서 같은 영수증 | UNIQUE는 **계정 무관 전역** 제약 → 거절 |
| 사진 일부만 변조해 다른 영수증처럼 위장 | OCR 신뢰도 미달 또는 QR 서명 검증 실패 → 거절 |

핵심은 **이미지 해시(파일 자체)가 아니라 분석으로 추출한 "텍스트"를 키로 쓴다**는 점이다. 사용자가 사진을 아무리 만져도 영수증의 인쇄된 글자는 안 바뀐다.

> ### 그럼 가짜 승인번호를 만들면?
>
> OCR 경로의 약점이다. 합성/위조한 영수증에 가짜 승인번호 11자리를 박아 올리면, 우리 서버는 그게 "진짜 발급된 번호"인지 직접 못 물어본다.
>
> **국세청 현금영수증 진위확인 API**는 일반 기업이 자유롭게 못 쓴다 (본인 인증 후 본인 영수증만 조회 가능). 그래서 이 영역은 **QR 경로로 우회**하는 게 정답이다 — 가맹점이 직접 서명한 QR 영수증은 위조 자체가 불가능하다.
>
> OCR 경로는 보조 수단으로 두고, 도입 초기에 의심 패턴 분석 + 사후 감사로 보완한다.

## 6. 가장 중요한 설계 결정 — 트랜잭션 처리

여기서부터가 진짜 시스템 설계의 묘미다.

### 단순한 발상

```
BEGIN
  INSERT receipts (pending)
  → Kaia mint() (1초 대기)
  UPDATE receipts (confirmed)
COMMIT
```

이게 직관적이다. 그런데 **블록체인 호출이 끝날 때까지 DB 트랜잭션이 열려 있다.** 의미는?

- DB 커넥션이 1초간 점유됨
- INSERT한 row 락 1초간 유지
- 동접 100명이 동시에 누르면 → 커넥션 풀 고갈 → 서비스 다운

### 4-Phase 분리 패턴

그래서 이렇게 쪼갠다:

| Phase | 단계 | 하는 일 |
|---|---|---|
| **1** | 6 | DB BEGIN → INSERT (status='신청') → COMMIT (락 즉시 해제) |
| **2** | 7~8 | Kaia mint 호출 → 거래번호 받음 |
| **3** | 9 | DB UPDATE (status='발행 중', 거래번호 저장) |
| **4** (비동기) | 11~12 | Kaia 확정 이벤트 수신 → DB UPDATE (status='완료') |

핵심은 **Phase 1에서 DB 트랜잭션을 끝낸 뒤** 블록체인 호출로 넘어간다는 점이다. DB 락은 수 ms만 잡혔다 풀리니 동접에 강해진다.

### 사용자에게는 Phase 3까지만 보여준다

블록체인 확정(Phase 4)은 1초 정도 더 걸린다. 사용자한테 끝까지 기다리게 하면 답답하다. 그래서 **Phase 3 시점에 "처리 시작했어요" 응답을 먼저 보낸다 (단계 10).** 그리고 Phase 4의 확정 이벤트가 오면 그제서야 푸시 알림으로 "토큰 N개 적립 완료!"를 알린다 (단계 13).

UX 입장에서는:
- 즉시: "적립 처리 중..." 토스트 표시
- ~1초 후: "토큰 5개 적립 완료!" 푸시 + 잔액 갱신

기다리는 1초 동안 사용자는 다른 화면으로 이동해도 된다.

## 7. 거래번호(txHash)는 만들고 / 검증하고 / 저장한다

블록체인 트랜잭션을 보내면 즉시 **거래번호(txHash)** 가 돌아온다 (단계 8). 단, 이건 **"접수증"** 일 뿐이다. 진짜로 처리됐는지는 모른다.

진위 확인은 **확정 이벤트**(단계 11)에서 이뤄진다. Kaia가 합의를 마치고 `Transfer(0x0, user, amount)` 이벤트를 emit하면 우리 서버의 이벤트 리스너 워커가 받는다. 이 시점에 비로소:

1. **거래번호가 진짜 처리됐다** 고 검증 완료
2. **검증된 거래번호와 적립 내역**을 DB에 영구 저장 (단계 12)
3. 사용자에게 푸시 (단계 13)

요약하면 거래번호는 이런 라이프사이클을 탄다:

```
[단계 8]  블록체인 → 서버 : 거래번호 회신 (접수증)
[단계 9]  서버 → DB        : 거래번호 임시 저장 (status='발행 중')
[단계 11] 블록체인 → 서버 : 확정 이벤트 → 거래번호 진위 검증
[단계 12] 서버 → DB        : 검증된 거래번호 영구 저장 (status='완료')
```

> Kaia는 IBFT 합의 기반으로 **1-block finality**, 즉 한 블록이면 확정이다. 비트코인이나 일반 PoS 체인처럼 "6블록 컨펌 대기" 같은 게 없어서 ~1초 만에 끝난다.

## 8. 부정 적립 방지 — 정리

다이어그램 우측 빨간 패널에 들어간 항목을 종합하면 이렇다:

| 공격 시나리오 | 막는 방법 |
|---|---|
| 같은 영수증 재업로드 | 영수증 번호 UNIQUE |
| 사진 변형 후 재업로드 | 이미지 무관, 분석 결과의 영수증 번호로 차단 |
| 다른 계정으로 같은 영수증 | UNIQUE는 계정 무관 전역 |
| 합성 / 위조 영수증 (QR) | 가맹점 시크릿 서명 → 위조 불가 |
| 합성 / 위조 영수증 (OCR) | 신뢰도 + 휴리스틱 + 사후 감사 |
| 오래된 영수증 재활용 | 결제일 7일 이내만 |
| 블록체인 직접 조작 | 발행 권한(MINTER_ROLE)은 서버 지갑만 보유 |

마지막 줄이 핵심이다. **일반 사용자는 토큰을 mint 할 권한이 없다.** Kaia 컨트랙트에 `onlyRole(MINTER_ROLE)` 같은 제약을 걸어서 서버 지갑(KMS 보관)만 호출할 수 있게 한다. 사용자가 자기 지갑으로 직접 mint를 시도해도 컨트랙트가 reject 한다.

## 9. 정리하며

13 단계짜리 시퀀스이지만 **본질은 4가지 결정**으로 줄어든다.

1. **DB 트랜잭션과 블록체인 호출을 분리한다.** 같이 묶으면 동접에 죽는다.
2. **사용자 응답은 Phase 3까지만** — Phase 4(확정)는 비동기로 푸시.
3. **이미지가 아니라 분석 결과(영수증 번호)를 키로** 중복 차단.
4. **QR(1순위) + OCR(2순위) 하이브리드** — QR 영수증은 위조 0%, OCR은 fallback.

생각보다 단순하지만, 막상 안 쪼갰을 때 어떤 일이 일어나는지를 알아야 이 분리가 왜 필요한지 보인다. 시퀀스 다이어그램은 그걸 보여주는 도구다.

> ### 이 시리즈의 한계
>
> 이 글은 **백엔드 + 블록체인 흐름** 관점이다. 실무에서는 추가로:
>
> - 가맹점 정산 (사장님이 받은 토큰을 현금화)
> - 토큰 가격 안정화 (스테이블 코인 페그? 가맹점 보장가?)
> - 고객 데이터 보호 (영수증 사진 보관/삭제 정책)
> - 회계·세무 (포인트 적립이냐 가상자산 발급이냐의 법적 구분)
>
> 같은 이슈가 줄줄이 따라온다. 그건 또 다른 글에서.

---

설계는 결국 "어디서 어디로 책임을 옮길지"의 게임이다. 책임을 적절히 쪼개면 시스템이 가벼워지고, 한쪽에 몰아두면 무거워져서 죽는다. 영수증 한 장 적립하는 데도 5개의 컴포넌트와 13 단계가 들어간 건, **각 단계가 하는 일을 다른 곳에 떠넘기지 않기 위해서** 였다.
